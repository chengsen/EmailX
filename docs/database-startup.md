# Database startup and search maintenance

Opening an existing store keeps its `messages_fts` index. GRDB's synchronized FTS creation hook rebuilds the index even when `ifNotExists` is true, so the application calls that hook only when the FTS table is absent. New stores still receive the same tokenizer, prefix indexes, columns, and insert/delete synchronization triggers.

The additive `vSelectiveFTSUpdates` migration replaces the update trigger. It indexes an update only when an indexed value or the SQLite rowid changes. Null-safe comparisons preserve text-to-NULL and NULL-to-text transitions. Read flags, interaction scores, download status, folder moves, and repeated writes of unchanged headers do not re-tokenize the message body. Folder unread-count triggers continue to operate independently.

The additive `vTrimLegacySubjects` migration cleans old subject whitespace once. Its first execution can scan a large existing store; later launches do not repeat that scan. Neither migration wipes mail, attachments, accounts, pending actions, or the existing index. Index creation for a new store and future index-format changes still require indexing work; changes to the search columns/tokenizer must use a new migration and keep the update trigger and `bm25()` weights aligned.

After an arm64 Release build, run `scripts/verify-database-startup.sh`. A custom DerivedData directory can be passed as its first argument. The script compiles the application's actual database source files and links the built GRDB object; no additional dependency download is needed. It operates exclusively on a temporary database and removes it afterwards.

The executable verifies an upgrade from the old unrestricted update trigger, one-time subject cleanup, reopen without index rebuilding, preservation of existing search results, no FTS writes for flags/scores/status or unchanged indexed values, all nine indexed columns, NULL transitions, accent folding, rowid changes, insert/delete search synchronization, unread-count updates, and an FTS external-content integrity check. SQL tracing first confirms that it can detect the old excessive update and initial index rebuild, so the absence checks cannot silently pass with a disabled trace.

For a reproducible comparison, run `scripts/benchmark-database-startup.sh [DerivedData] [baseline-ref]` (baseline defaults to `47def58`). The script compiles historical and current application database implementations against the same Release GRDB object. Only the historical migration method's visibility is changed to permit invocation. Each variant creates an isolated database containing 1,000 or 10,000 messages with a 2,589-byte body, completes initial migrations outside timing, and takes three samples of repeated schema/migration startup and 1,000-row interaction-score updates. Results are written to `build/verification/database-benchmark/baseline.json` and `optimized.json`; both variants finish with an FTS integrity check.

On 2026-10-01, warm-pool schema/migration medians changed from 26.466 ms to 0.111 ms for 1,000 messages, and from 383.169 ms to 0.132 ms for 10,000 messages. The corresponding 1,000-row score updates changed from 65.829 ms to 13.370 ms and from 100.219 ms to 13.977 ms. These isolate database work and include transaction completion. They are not full application startup measurements, cold filesystem-cache measurements, or results from a user's real mailbox.
